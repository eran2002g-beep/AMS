## ✅ Acceptance Criteria — Detailed Analysis

### AC1 — Auto-generate unique Employee ID on record creation

> Given a new employee is created, when the record is saved, then the system shall generate a unique employee ID.

**Status: ✅ MET**

**How it works:**

1. `POST /employee/create` in `employeeRoute.js` calls `employeeService.createEmployee(req.body)`.
2. Inside `createEmployee()` in `Employeeservice.js` (L32–37), all existing `employeeId` values are fetched from the database.
3. `generateNextEmployeeId()` computes the next ID in the `EMP001`, `EMP002`, `EMP003`… sequence.
4. The new ID is explicitly passed into `Employee.create({ employeeId: nextEmployeeId, ... })`.
5. The `employeeId` column in the database schema is `allowNull: false, unique: true` — the database enforces uniqueness at the storage level.

**ID generation logic (`employeeIdGenerator.js`):**

```js
const generateNextEmployeeId = (existingIds = []) => {
  const matches = (existingIds || [])
    .filter((value) => typeof value === 'string')
    .map((value) => value.trim())
    .filter((value) => /^EMP\d+$/.test(value))
    .map((value) => Number(value.replace(/^EMP/, '')))
    .filter((value) => Number.isInteger(value) && value > 0);

  const nextNumber = matches.length > 0 ? Math.max(...matches) + 1 : 1;
  return `EMP${String(nextNumber).padStart(3, '0')}`;
};
```

- Filters out any non-`EMP`-format strings before computing the max.
- Starts at `EMP001` if no employees exist.
- Pads to at least 3 digits (e.g., `EMP001`, `EMP010`, `EMP100`).

### AC2 — Validation messages when required fields are missing

> Given required fields are missing, then validation messages shall be displayed.

**Status: ✅ MET**

**How it works:**

`validateEmployeePayload()` in `employeeValidation.js` is called with `{ requireAllFields: true }` during employee creation. It checks each field and pushes descriptive error messages into an array:

| Field | Validation |
|-------|-----------|
| `firstName` | Required; cannot be blank |
| `lastName` | Required; cannot be blank |
| `email` | Required; must match email regex |
| `phone` | Optional; must match phone format `[0-9+()-\s]{7,15}` |
| `department` | Optional when present; cannot be empty string |
| `role` | Must be `'admin'` or `'employee'` |
| `roster` | Must be a boolean |

All collected errors are joined with `;` and thrown as a single `Error`. The route catches it and returns:

```json
HTTP 400
{
  "error": "firstName is required; email must be a valid email address"
}
```

### AC3 — Auto-generate Employee ID if a record has none

> Given an employee record exists without an Employee ID, when the system validates the employee data, then a unique Employee ID shall be automatically generated by the system.

**Status: ✅ MET**

**How it works:**

A Sequelize `beforeValidate` lifecycle hook in `Employee.js` (L89–101) acts as a safety net:

```js
hooks: {
  beforeValidate: async (employee) => {
    if (!employee.isNewRecord || employee.employeeId) return;

    const existingEmployeeIds = await Employee.findAll({
      attributes: ['employeeId'],
      raw: true,
    });

    employee.employeeId = generateNextEmployeeId(
      existingEmployeeIds.map((item) => item.employeeId)
    );
  },
},
```

- Fires **before** Sequelize's `allowNull` validation check — ensuring the field is populated in time.
- Only runs if the record is **new** (`isNewRecord`) **and** does not already have an `employeeId`.
- Directly satisfies the AC scenario where a record is constructed without an ID.

### AC4 — Employee ID remains linked to the employee profile

> Given employee data is stored, then the employee ID shall remain linked to the employee profile.

**Status: ✅ MET**

Three mechanisms enforce this:

1. **Database schema** (`Employee.js` L22–26):  
   ```js
   employeeId: {
     type: DataTypes.STRING,
     allowNull: false,
     unique: true,
   }
   ```
   The column cannot be set to `null` or duplicated at the DB level.

2. **Update endpoint** (`Employeeservice.js` L136–173):  
   The `updateEmployee()` function only accepts `firstName`, `lastName`, `email`, `phone`, `department`, `role`, and `roster` as updatable fields. `employeeId` is **never** included in the update payload — it cannot be changed via the API.

3. **Soft delete** (`Employeeservice.js` L108–128):  
   `deleteEmployeeById()` sets `isActive = false` instead of physically deleting the row. The `employeeId` and all associated data remain in the database, preserving the link between the ID and the employee's historical records.

### Issue 1 — Duplicate ID Generation Logic (Code Smell)

**Severity:** ⚠️ Medium (no current bug, but a maintenance and race-condition risk)

**Description:**  
`generateNextEmployeeId()` is called in **two places** during a single `createEmployee()` operation:

| Location | Line | Action |
|----------|------|--------|
| `Employeeservice.js` | L32–37 | Fetches all IDs, generates next one, passes it into `Employee.create()` |
| `Employee.js` (`beforeValidate` hook) | L92–101 | Also fetches all IDs and generates next one if `employeeId` is missing |

**Why it's not breaking today:**  
Because the service explicitly sets `employeeId` before calling `Employee.create()`, the hook's guard condition `if (!employee.isNewRecord || employee.employeeId) return` exits early — the hook's generation path is never reached in normal flow.

**Risk:**  
Under high concurrent load, two simultaneous `createEmployee()` calls could both read the same "max" ID before either writes to the database — resulting in a duplicate key collision (the DB `unique` constraint would catch it, but the user would receive an error).

**Recommendation (for backlog):**  
Remove the ID generation logic from `Employeeservice.js` (L32–37) and rely solely on the `beforeValidate` hook. Or implement a proper sequence/transaction.

---

### Issue 2 — Filename Casing Inconsistency

**Severity:** ⚠️ Medium (breaks on Linux/Docker deployments)

**Description:**

| Item | Value |
|------|-------|
| Actual filename on disk | `src/services/Employeeservice.js` |
| Import path in `employeeRoute.js` | `require('../services/employeeService')` |

**Why it works on Windows:**  
Windows file system is case-insensitive, so `Employeeservice.js` and `employeeService.js` resolve to the same file.

**Why it will break on Linux/Mac:**  
Linux file systems are case-sensitive. This import will throw `MODULE_NOT_FOUND` when deployed to any Linux server or Docker container.

**Recommendation (for backlog):**  
Rename the file to `employeeService.js` (lowercase `e`, capital `S`) to match the import convention used everywhere else.

### Issue 5 — `pg` SSL Deprecation Warning (Non-Breaking)

**Severity:** ℹ️ Informational

**Description:**  
When the server loads, the `pg` library emits:

```
Warning: SECURITY WARNING: The SSL modes 'prefer', 'require', and 'verify-ca'
are treated as aliases for 'verify-full'...
```

This is a deprecation notice from `pg-connection-string` and does not affect current functionality. It will become a breaking change in `pg` v9 / `pg-connection-string` v3.

**Recommendation:**  
Add `sslmode=verify-full` explicitly to the database connection string before upgrading `pg`.
